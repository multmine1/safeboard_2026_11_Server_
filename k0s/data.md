# Хранилища и PostgreSQL

После настройки гостей, PKI/Vault и k0s выполните из корня проекта
([порядок подготовки Secrets](secrets.md)):

```console
python scripts/applications.py
```

Компоненты infra/public развёрнуты на VM.

| Сеть | Данные PostgreSQL | Начальная БД / владелец | Файлы NFS |
|---|---|---|---|
| infra | 32 GiB, один экземпляр на db VM | forgejo | Forgejo: `/srv/data/forgejo` |
| public | 32 GiB, один экземпляр на db VM | portfolio и registry, отдельные роли | Портфолио: `/srv/data/portfolio` |

## Локальные PV

Официальный local-path-provisioner создаёт PV класса `local-fast` только на двух
db VM, внутри `/srv/fast/kubernetes`. Родительский `/srv/fast` монтирует этап
подготовки гостей; это отдельный диск NVMe. На остальных узлах путь для PV
не объявлен. Каталоги томов создаёт штатный helper provisioner.

`WaitForFirstConsumer` согласует PV с размещением Pod. CNPG получает селектор
конкретной db VM и её сетевые метки. PostgreSQL использует локальный диск;
NFS предназначен для файлов приложений.

Политика `Retain` сохраняет PV после освобождения PVC. Удаление VM или её диска
управляется отдельно через OpenTofu. Размер PVC не является файловой квотой
local-path-provisioner; необходимо следить за заполнением диска. Автоматическое
расширение CNPG PVC выключено. Один экземпляр PostgreSQL не обеспечивает
отказоустойчивость, а сохранённый PV не заменяет резервную копию.

## Подключение к PostgreSQL

CNPG создаёт Service на адресе db VM, порт 5432, с локальным backend. Адреса
и доступные клиенту endpoints находятся в сгенерированных Ansible host_vars,
поле `connections`. Межсетевые пути и трансляции применяют роутеры.

Для приложений внутри namespace доступны штатные Services
`postgres-infra-rw` и `postgres-public-rw` соответственно.
Маршрут к адресу Pod не расширяет разрешения сетевой политики.

Пароль владельца создаёт CNPG. В соответствующем namespace он хранится в Secret
`postgres-infra-app` или `postgres-public-app`, поля
`username` и `password`. Приложения должны ссылаться на Secret; приватные значения
не копируются в исходные JSON, Chart values или notebook. Удаление/восстановление
Secrets согласуется с резервным копированием PostgreSQL.

На controller можно посмотреть состояние без вывода секретов:

```console
sudo k0s kubectl get clusters.postgresql.cnpg.io --all-namespaces
sudo k0s kubectl get pvc --all-namespaces
sudo k0s kubectl get pv
```

## NFSv4

Ansible готовит экспортированные каталоги на SSD и применяет NFSv4 через
`nfs-server`. NFSv3 и UDP отключены. Владение файловыми каталогами — UID/GID 1000,
с `root_squash`; разрешены только явно указанные клиенты общей сетевой политики.
Их адреса, включая адрес после NAT, подставляет C++.

Перечень экспортов: `configs/generated/k0s/applications/deployment.json`,
`applications.nfs-infra.guest` и `applications.nfs-public.guest`.
Доступ использует TCP 2049 через роутер своей сети.

Повторный этап обновляет подготовленные файлы и экспортированные разрешения.
Отключение host workload сохраняет его данные и ранее применённые файлы ОС;
для остановки NFS требуется отдельное действие администратора. Монтирование
этих файловых хранилищ Forgejo и портфолио подготовлено через статические NFS
PV/PVC. C++ получает путь клиента из одного объявления серверного экспорта.

Перед использованием проверяются реальная запись в PV/NFS, разрешённые и
запрещённые клиенты, перезапуск db VM и восстановление данных. Локальные GTest,
Helm rendering и проверка схем эти сценарии не подтверждают.

При развёртывании проверены запись и чтение обеих PostgreSQL и NFSv4 приложений.
После контролируемой перезагрузки infra/db контрольные SQL-записи и файлы
сохранились; диагностические данные удалены. Публичная db VM в этой проверке
не перезагружалась. Восстановление из внешней резервной копии не проверено.

Дополнительно подготовлены статические локальные PV: VictoriaMetrics — 32 GiB
на NVMe, VictoriaLogs — 64 GiB на SSD, Registry — 128 GiB на SSD своей db VM.
У них также `Retain` и привязка к конкретной VM. Valkey работает как
непостоянный кеш, без AOF/snapshots и отдельного тома данных.
