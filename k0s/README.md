# Запуск кластера

Сначала выполните шаги окружения, генерации, OpenTofu и настройки гостей из
[основного README](../README.md). Все команды ниже запускаются из корня проекта на Mac.
На живом кластере работают 12 узлов и четыре активных router workload.

```console
python scripts/k0s.py
```

Ansible устанавливает закреплённый k0s, запускает controller, публикует сетевые
манифесты и присоединяет работающие worker. Затем последовательно публикуются
роутеры: главный, management, infra и public.
Используются готовый Debian slim для init и официальный CoreDNS, без сборки образа.
Конкретные версии, digest, пути, ресурсы и таймауты находятся в исходном `site.json`.

Наборами ресурсов владеет штатный Manifest Deployer k0s. Удаление ресурса из
сгенерированного набора приводит к его удалению из Kubernetes. Чужие каталоги
манифестов и таблицы nftables не очищаются.

## Изменение конфигурации

Измените исходные JSON, повторите генерацию, просмотр плана OpenTofu и необходимые
этапы применения. Сетевые файлы роутера обновляет init-контейнер при смене ревизии
DaemonSet. Он сохраняет netplan, nftables и sysctl на диске гостя, применяет их и
останавливает временный systemd CoreDNS. Работающий CoreDNS запускается в Pod.

Обычный `scripts/guests.py` после передачи владения пропускает сетевую настройку
роутера. Настройка пользователей, пакетов и остальных файлов ОС остаётся доступна.
Init-контейнер применяется при запуске Pod; непрерывное исправление произвольных
ручных изменений host-файлов не реализовано.

Включение и штатное выключение VM выполняются через Cockpit; `domain.running`
задаёт только начальное питание новой VM. UUID, ASN, Pod-пул и BGP-соседства
сохраняются независимо от питания. Ansible читает текущие running domains из
libvirt и выбирает узлы по готовым C++ путям: должны работать целевая VM и все
её роутеры. Состояние SSH и служб проверяется уже штатным подключением и ожиданиями.
Системные DaemonSet ожидаются только на выбранных работающих узлах нужных ролей;
для остальных системных workloads сохраняется штатное ожидание rollout.
Автоматического включения, TTL и планировщика жизненного цикла VM нет.

## Восстановление

Перезагрузка роутера использует сохранённые локальные маршруты и firewall до
восстановления API. Образы init/CoreDNS уже находятся в локальном containerd.
SSH inventory использует адреса и рассчитанный путь через гипервизор; разрешение
имён Kubernetes для подключения не требуется.

Для повторного применения сохранённого payload на самом роутере:

```console
sudo ansible-playbook /var/lib/skeleton/router/apply.yml
```

Путь выше соответствует текущему `router_runtime.apply_playbook`. Этот файл
восстанавливает сохранённую конфигурацию хоста и оставляет DNS во владении k0s.
Если API/Pod недоступны, временный DNS можно запустить на роутере:

```console
sudo systemctl stop k0sworker
sudo systemctl start coredns
```

Corefile временного DNS сохранён на диске и не использует Kubernetes API.
После устранения причины:

```console
sudo systemctl stop coredns
sudo systemctl start k0sworker
```

Откат сетевой политики выполняется восстановлением предыдущих исходных JSON,
повторной генерацией и запуском `scripts/k0s.py`. Один `kubectl rollout undo`
не восстанавливает изменённые ConfigMap. Для потери IP-доступа потребуется
локальная консоль VM или доступ через средства гипервизора.

На текущем стенде проверены запуск, применение исправлений, запрещённые направления
и перезагрузка главного роутера при остановленном API. Доступ по IP и firewall
восстановились до запуска control plane; после его запуска восстановились DNS
и приложения. Эти результаты получены на VM отдельно от GTest.


## Прикладные компоненты

После готовности кластера и [подготовки Vault](secrets.md):

```console
python scripts/applications.py registry forgejo
```

После настройки токенов Registry в Vault — весь активный набор:

```console
python scripts/applications.py
```

Подготовлен 21 workload: CI не применяется, пока его VM выключена. Используются
официальные закреплённые компоненты. Текущий список и доступ — [services.md](services.md),
данные — [data.md](data.md), ручной запуск CI — [ci.md](ci.md).

C++ рассчитывает namespace, размещение, адреса и зависимые этапы. Ansible публикует
готовые наборы и ждёт нужную ревизию. Архивы charts проверяются по SHA-256;
релизами управляет встроенный Helm controller k0s. Приватные значения не
помещаются в Chart values или ConfigMap.

`enabled: false` удаляет набор при следующем полном применении. Выключение VM
сохраняет набор и исключает из текущего применения приложения этой VM и их
зависимых потребителей. Выборочный запуск
`applications.py NAME` применяет подготовленные зависимости и не удаляет другие
наборы; выключенные зависимости нужно сначала запустить вручную. Полное применение
очищает только свои устаревшие каталоги манифестов.
